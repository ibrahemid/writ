# ADR-022: Line-shape editor open mode for responsive large-file opens

**Status:** Accepted. Amended 2026-10-13: the editor publishes a version, not its text, and every reader takes the document in its own idle work ("Amended: no text is published per keystroke"). Amended 2026-10-14: limits per capability, tab states kept across switches, saves without the whole text ("Amended: tiers per capability"). Amended 2026-10-15: one state per tab per pane ("Amended: two panes").
**Date:** 2026-06-25

## Context

The editor open mode is tiered by byte size in `writ-core` (`classify_file`): `Normal` (≤ 5 MiB) gets the full CodeMirror feature set; `LargeFile` / `LargeFileConfirm` above that drop syntax highlighting, line wrapping, and typography. The frontend mirrored only that byte threshold when mounting the view.

Byte size is the wrong dimension for one common shape. A minified bundle — a single multi-hundred-kilobyte line of JS/JSON/CSS — is small in bytes and so opened as `Normal`, with `lineWrapping`, the language extension (Lezer parse), and bracket matching all active. CodeMirror's per-line layout and measurement cost is superlinear in line length, so mounting one giant line froze the view thread for seconds while the editor was already small enough to dodge every existing safeguard. This is the "hangs on a long file" report, and the byte tier does not see it.

Component measurement of the open path (`@codemirror/state`, real packages) separated the two regimes:

- Many short lines: `EditorState.create` is 55 ms at 30 MiB, 269 ms at 100 MiB; full-document `toString` adds 37–68 ms. Slow but bounded, and these files are already restricted by the byte tier.
- One pathological line: document construction is ~1 ms, but the DOM layout of that line under wrapping + language is the multi-second freeze.

So the freeze is a line-shape problem, not a byte-count one. Document construction is not the freeze, so it is left alone; the fix is the editor feature set the document is mounted with.

## Decisions

### A frontend-only `LongLines` open mode

`editorModeForContent(buffer, content)` (`src/editor/large-file.ts`) resolves the mode from metadata and the loaded content: read-only → `Binary`; size over the byte threshold → `LargeFile`; otherwise, if any line exceeds `MAX_NORMAL_LINE_LENGTH` (10 000 columns, the long-line tokenization cutoff editors like VS Code use) → `LongLines`; else `Normal`. `hasLongLines` scans with an early exit, so a pathological file is detected at its first long line, and the full scan only runs for buffers already under the byte threshold.

`LongLines` is a frontend-only variant of `FileOpenMode`. The backend tiers stay byte-only and never emit it — the byte classification has no content in hand at `classify_path` time, and plumbing a content-shape flag back through the buffer record and IPC would add a schema dimension for a decision the editor already makes where the content lives. The frontend already derived open mode from buffer metadata at mount; this extends that derivation with the one input (content) the backend lacks. `LongLines` joins `LargeFile` / `LargeFileConfirm` in the restricted feature set (no wrap, no language, no typography, longer autosave debounce) and shows a "Long lines · syntax off" status chip so the restriction is never silent.

### Restrict the feature set, not the open-time publish

All buffers publish `currentText` once on open so the published text always matches the buffer id set immediately after it (the `#97` ordering invariant). The per-keystroke materialization — the actual jank for restricted buffers — stays deferred on the update path (`scheduleRestrictedContentPublish`, added in #152 without a record of its own; ADR-020 covers that change's FTS reindex deferral, not this publish); the bounded one-time publish on open does not. The responsiveness win comes entirely from the restricted feature set, not from deferring the open publish.

### Amended: no text is published per keystroke

Before this amendment every tier still paid for the whole text as it was edited (the editor-perf audit, 2026-10-03). `Normal` published `doc.toString()` per keystroke; the restricted tiers (`LongLines`, `LargeFile`, `LargeFileConfirm`) published it 400 ms after the last edit. Each publish fed, while they were on screen, a word count and a character spread of the whole text and a token-estimate IPC carrying it, and, while the preview was open, a debounced render whose size gate encoded it as UTF-8. Beside the publish, each `Normal` edit queued a spelling check of the whole text, and 150 ms after the last edit the dirty check hashed the whole text with SHA-256. `currentText` and the restricted publish timer are gone.

- **A version, not the text.** The editor store holds `docVersion`, which the view's update listener moves on every document change. Readers take the document itself (`liveDoc()`, the view's `Text`) when their own idle work runs, so no tier turns the document into one string inside a keystroke. The `#97` ordering invariant is unchanged: the view is registered before `currentBufferId` names its buffer, so `liveDoc()` is that buffer's document whenever the id says so.
- **Counts.** `src/editor/document-counts.ts` counts words and characters from the document's own line strings (whitespace as `\s` matches it, characters as code points), in slices of at most 6 ms that resume inside a line and across versions of the document. Finished subtrees are cached by identity, so a recount after an edit reads the changed path and its sibling leaves, not the document. Counting runs only while the word count or token estimate is on screen. A recount starts once the document has gone 120 ms without a change; a change during the wait or during a recount starts the wait again, so nothing is counted while keys keep arriving. In `LargeFile` and `LargeFileConfirm` an unfinished count shows a projection from the part counted, prefixed `≈` and rounded to two significant figures. A Worker was weighed and not used: the document reaches a Worker only as a copy of its text, an allocation the size of the document, which is the cost this removes.
- **Token estimate.** Computed from the counts with the blend `writ_core::prompt::estimate_tokens` uses; `crates/writ-core/tests/fixtures/token-estimates.json` holds the two to the same answers. No IPC carries the text for it. The two whitespace sets differ on U+0085 and U+FEFF, which the fixture leaves out.
- **Dirty.** The document is compared with the text the note's file is known to hold after a 150 ms pause, and a write's digest from Rust is the acknowledgement that the file holds what that write carried (ADR-033 §6). The comparison (`src/editor/same-document.ts`) gives `Text.eq`'s answer, but where the two trees line up child by child it compares each pair of children on its own and skips the children both hold, so an edit near the top and one near the bottom, both undone, read the two edited stretches rather than the document between them. The frontend computes no digest; `src/lib/doc-hash.ts` is gone.
- **Held typing.** Typing into a note whose saves a bar is holding keeps the document as it stands. It becomes a string when the unsaved-text journal takes it after a pause, when the tab is switched away from, or when something reads it.
- **Spelling** sends the paragraphs edited since the last check, each widened to its paragraph (at most 32 lines each way) and to any code block it touches, and replaces the marks inside them only. Edits that leave more than 16 stretches unchecked (a Replace All, typing with many cursors) are held as one stretch from the first to the last, so the bookkeeping, the requests and the landing of the results stay bounded by that number rather than by the number of changes. A change to the dialect or the ignore list sends the whole note again: the marks outside an edit would keep the old verdict otherwise.
- **Preview** measures the document's UTF-8 length from its strings, stopping past the refusal limit, skips a render of a document equal to the last one rendered, and reads the text only when it renders. A tab with no document in the editor (its open has not answered) renders as empty, as it did when the editor published an empty text for it.
- **Frontmatter.** The end of the frontmatter block is a state field mapped through changes; an unclosed block checks only the changed lines for a closing fence.
- **Right-click** looks for `{{placeholders}}` line by line, and not at all in the large tiers.

### Amended: tiers per capability

`LongLines` no longer turns everything off. `featuresFor(mode, longestLine, overrides)` (`src/editor/large-file.ts`) is the one record the extensions and the status-bar chip read. Per-line decorations (Markdown rendering, links, wikilinks, direction) skip only lines over 10,000 characters (`rangesWithinLineLimit`); wrapping and highlighting stay on while the longest line is within 1,000,000 characters, set from the editor-perf audit's one data point (a 5 MiB line: 1.3 s one-time wrap measure, about 0.25 µs a character, so the limit budgets about 250 ms; highlighting added 17 ms a keystroke, about 3 ms at the limit). Spell check stays off for the file. The byte tiers are kept (O-5). The chip opens a menu that lists what is off and why and turns wrapping and highlighting on or off for the file; those choices last for the session, as the buffer row has no column for them. With the status bar hidden, the tab tooltip names the tier. One view serves every tab: each tab's `EditorState` is kept with a scroll snapshot and restored with `view.setState` when the text the load decides on equals it, within a 64 Mi code unit budget that drops large-tier states first; `cursor_pos` and `scroll_pos` hold where a tab was left for a later session. A transaction moving 64 KiB or more re-reads the tier from the document (UTF-8 length, longest line) and the chip offers the switch, which reconfigures the view in place. `save_buffer_content` takes the text as a raw body; the large tiers and `LongLines` send the change set since the last landed write, or since the open's read when nothing has landed (`save_buffer_changes`), which Rust applies to the file's text after checking its digest against the one that write or the open's `note_disk_state` returned and its bytes against the write guard's record, then saves through the same encode, guard and journal path. A refused change set is sent again whole. `size_bytes` follows every write.

### Amended: two panes (ADR-056)

One view serves every tab of a pane. Each tab keeps one `EditorState` per pane it is open in, in one cache keyed by pane and tab under the same 64 Mi budget. A note open in both panes shares its document: the second pane starts from the first pane's `Text`, and each change is mirrored into the other pane's view or kept state without entering its undo history. A tab moved to the other pane takes its state with it, reconfigured with that pane's extensions.

## Consequences

- A small minified file opens responsively, in restricted mode, instead of freezing the editor. The trade is syntax highlighting on files whose single-line shape makes highlighting both expensive and near-useless — the same trade every major editor makes, and it is surfaced in the status bar.
- The line-shape decision is a pure, unit-tested function; the escaped bug (byte-only classification) is covered at that layer.
- The byte tiers and the confirm-dialog gate for 50–500 MiB files are unchanged.
